# Process-Control Notes

## Traceability chain

A useful way to read the case study is as one continuous traceability chain:

```text
Stakeholder Need
      ↓
Requirement Baseline
      ↓
Plan / Schedule / Budget
      ↓
Execution Data + Risks
      ↓
Quality Verification
      ↓
Approved Corrective Change
      ↓
Controlled Version / Audit Trail
```

## Why each process area matters

**Requirements Management (RM)** prevents stakeholder needs from being forgotten, changed informally, or implemented without an approval trail.

**Project Planning (PP)** converts requirements into explicit commitments for cost, schedule, and activity scope.

**Project Monitoring and Control (PMC)** compares actual performance with those commitments and triggers corrective action when necessary.

**Process and Product Quality Assurance (PPQA)** provides an objective check that both the process and resulting deliverables satisfy defined expectations.

**Configuration Management (CM)** protects the integrity of plans, lists, registers, and other project artifacts by controlling versions and documenting authorized changes.

## Feedback-loop interpretation

The process areas form a feedback system rather than a one-way checklist. Monitoring and quality findings may require changes to the plan. Those changes should then be reviewed, approved, versioned, and reflected in the controlled baseline before work continues.
